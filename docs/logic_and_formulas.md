# Логика проектов Карпова: статистика, формулы и порядок действий

Этот файл объясняет не только что посчитать, но и зачем нужен каждый шаг.

## Общий алгоритм A/B-теста

1. **Определить единицу анализа.** Для конверсии и ARPU нужна одна строка на
   пользователя. Транзакции сначала агрегируем по `uid`.
2. **Проверить качество данных.** Смотрим пропуски, дубли, даты, пересечения
   пользователей между группами и соответствие сумм выручки.
3. **Проверить баланс групп.** Если группы различались ещё до эксперимента,
   разницу нельзя уверенно приписать тесту.
4. **Проверить контроль с контролем (A/A).** После этого контрольные группы
   можно объединить для большей статистической мощности.
5. **Посчитать эффект и `p-value`.** Смотрим также размер эффекта и интервал.
6. **Принять решение по основная метрика.** Для денег обычно главная метрика —
   ARPU, а конверсия и ARPPU помогают объяснить результат.

## Основные формулы

```text
CR   = число пользователей с оплатой / все пользователи
ARPU = вся выручка / все пользователи
ARPPU = вся выручка / платящие пользователи
absolute_effect = test - control
relative_effect = (test / control - 1) * 100%
```

Если `payer` — булев столбец, `experiment["payer"].mean()` сразу даёт CR:
`True` трактуется как 1, `False` — как 0.

Для конверсии абсолютный эффект показываем в процентных пунктах: разница между
0.0339 и 0.0440 равна `-1.02 п.п.`.

## Статистические тесты

### Доли: z-тест пропорций

Используем для CR. Нулевая гипотеза: конверсии в тесте и контроле одинаковы.

```python
from statsmodels.stats.proportion import proportions_ztest

z_stat, p_value = proportions_ztest(
    [test_group["payer"].sum(), control_group["payer"].sum()],
    [len(test_group), len(control_group)],
)
```

Доверительный интервал разницы долей:

```python
from statsmodels.stats.proportion import confint_proportions_2indep

interval = confint_proportions_2indep(
    test_group["payer"].sum(), len(test_group),
    control_group["payer"].sum(), len(control_group),
    method="wald",
)
```

### Средние: t-тест Уэлча

ARPU и выручка имеют длинный хвост, поэтому используем t-тест Уэлча — он не
требует одинаковых дисперсий в группах.

```python
from scipy import stats

arpu_test = stats.ttest_ind(
    test_group["total_revenue"],
    control_group["total_revenue"],
    equal_var=False,
)
```

`arpu_test.pvalue` показывает, можно ли считать отличие средних случайным.

### Категории: хи-квадрат

Для проверки баланса по стране или полу строим таблицу частот:

```python
table = pd.crosstab(experiment["group"], experiment["country"])
chi2, p_value, dof, expected = stats.chi2_contingency(table)
```

## Проект 1 — мобильная игра

### Удержание

1. Переводим Unix-время в дату.
2. Считаем `day = auth_date - reg_date`.
3. Формируем когорту по дате регистрации.
4. Считаем уникальных игроков по дням жизни.

```text
Удержание когорты в день N = активные игроки в день N / размер когорты
```

Берём только полностью наблюдаемые когорты, иначе поздние регистрации будут
искусственно иметь низкий D7 или D14.

В A/B-части проекта 1 `ARPU` — основная метрика, конверсия и `ARPPU` —
диагностические. Крупных плательщиков не удаляем после просмотра результата: их происхождение —
отдельная проверка качества эксперимента.

## Проект 2 — механика оплаты и SQL-сегментация

1. Объединяем группы и дополнительный файл назначений.
2. Проверяем дубли пользователей и отсутствие группы.
3. Берём активных пользователей как популяцию анализа.
4. Присоединяем оплаты через `LEFT JOIN` и ставим ноль тем, у кого оплаты нет.
5. Считаем CR, ARPU и ARPPU.

`LEFT JOIN` сохраняет активных пользователей без оплаты — они нужны в знаменателе
конверсии и ARPU. В SQL заказы и события сначала агрегируются отдельно по
`customer_id`, чтобы не получить many-to-many размножение строк. `COALESCE`
ставит нули, а `CASE` проверяет сегменты сверху вниз.

## Проект 3 — новая цена премиум-подписки

В транзакциях один `uid` может встречаться несколько раз, поэтому сначала
агрегируем их до пользователя. Для общей выручки используем `users.total_revenue`
после reconciliation: в исходнике есть пустые строки, повторы и локальные
расхождения. Точные повторы нельзя удалять автоматически — они могут быть
реальными повторными покупками.

Основные метрики:

- `CR payer` — любая оплата;
- `CR premium` — покупка `premium_no_trial`;
- `ARPU` — общая выручка на участника;
- `ARPU обычного премиума` — выручка обычного премиума на участника;
- `CR trial` — контрольная метрика, потому что цена trial не менялась.

ARPPU не является главным критерием: он считается только среди уже оплативших.
Цена может повысить чек небольшой группы и одновременно снизить число
покупателей.

Итог проекта 3: payer CR снизился примерно с 4.40% до 3.39% (`p = 0.0059`),
CR обычного премиума — с 2.34% до 1.56% (`p = 0.0033`). ARPU вырос с 523.21 до
534.08, но различие незначимо (`p = 0.907`). Текущую цену не раскатываем.

## Как читать результат

- `p-value < 0.05` — различие статистически заметно при выбранной модели;
- `p-value >= 0.05` — недостаточно оснований объявлять эффект доказанным;
- знак эффекта показывает направление;
- интервал показывает диапазон правдоподобных значений;
- статистическая значимость не равна бизнес-значимости: важны размер эффекта,
  риск и долгосрочный LTV.
