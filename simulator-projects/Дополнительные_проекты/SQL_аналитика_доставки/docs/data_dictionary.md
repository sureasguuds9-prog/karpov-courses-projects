# Словарь данных и правила

## Связи таблиц

- `orders.order_id = user_actions.order_id`
- `orders.order_id = courier_actions.order_id`
- `user_actions.user_id = users.user_id`
- `courier_actions.courier_id = couriers.courier_id`
- `UNNEST(orders.product_ids) = products.product_id`

## Гранулярность

| Сущность | Одна строка |
|---|---|
| `orders` | один заказ |
| `user_actions` | одно действие пользователя с заказом |
| `courier_actions` | одно действие курьера с заказом |
| `users` | один пользователь |
| `couriers` | один курьер |
| `products` | один товар |

Перед объединением таблиц действий они агрегируются до одного ряда на заказ. Это защищает суммы и количество заказов от размножения строк.

## Принятые определения

- Создание заказа: `user_actions.action = 'create_order'`.
- Отмена: существует `user_actions.action = 'cancel_order'` для того же `order_id`.
- Доставка: существует `courier_actions.action = 'deliver_order'`.
- Активный пользователь дня: пользователь с любым действием в `user_actions`.
- Платящий пользователь дня: пользователь, создавший хотя бы один неотменённый заказ.
- Дата выручки: дата создания заказа, а не дата доставки.

## Проверки перед публикацией

1. Убедиться, что `order_id`, `user_id`, `courier_id`, `product_id` имеют ожидаемую уникальность.
2. Проверить, что после `UNNEST` все товары находятся в `products`.
3. Сравнить число заказов до и после каждого `JOIN`.
4. Проверить границы дат и отсутствие будущих дат.
5. Убедиться, что деление защищено через `NULLIF`.
6. Не называть доходностью метрику, в которой не учтены расходы.
